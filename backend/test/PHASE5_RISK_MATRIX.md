# VibeHue — Phase 5 risk matrix

Status: planning only, 2026-10-28. Severity is a proposed engineering/business triage level, not a verified production incident. References use paths under `backend/` unless prefixed `frontend/`.

| ID | Severity | Risk and current evidence | Impact | Proposed control / test | Gate owner and rollback |
| --- | --- | --- | --- | --- | --- |
| R1 | Critical | `digital_contracts` application DB historically has unique `bookingId_1`; V2 requires unique `(bookingId,providerId,scope)`. Current service refuses unsafe indexes. | Multi-provider prepare fails or migration corrupts legacy assumptions. | Read-only index/duplicate scan, backup/restore rehearsal, reviewed idempotent migration, exact index verification on separate DB first. | DBA + backend; flag OFF, stop writes, restore only with reconciliation approval. |
| R2 | Critical | Template and provider AUTO mechanism are DRAFT; legal/business meaning of consent and formation unresolved. | Misleading “signed” claim or issuing unapproved terms. | Explicit versioned wording approval; keep offer issuance blocked until approved; separate `acceptedAt`, `formedAt`, `effectiveAt`, `paidAt`. | Product/legal; keep flag OFF, preserve evidence. |
| R3 | Critical | `PaymentsService.createPaymentLink` returns existing pending link before new checks, and zero-value payment finalizes immediately. | Bypass consent/hold checks. | Shared readiness/binding guard before existing-link reuse, new link and zero-value finalization; regression tests for each. | Backend payments; disable new V2 initiation, reconcile existing intents. |
| R4 | Critical | `GET /payments/:code/status` auto-confirms pending sandbox payment; admin, simulator and webhook call central `confirmPayment`. | Controller-only guard is bypassed. | Put guard in service; route all finalization through one idempotent gate; HTTP/e2e inventory test. | Backend payments; feature flag OFF for new V2 bookings, continue money reconciliation. |
| R5 | Critical | `finalizeAfterPayment` updates payment, booking, inventory, voucher, settlement/notification across steps; not atomic as one workflow. | Money succeeds while rental/contract finalization fails. | Durable finalization journal/outbox, retry and manual review; failure injection after each step, assert DB and external side effects. | Payments/operations; stop new V2 links, continue recovery worker. |
| R6 | High | `booking-status.service.ts` expiry cleanup reads then `updateMany` by IDs; `bookings-scheduler.service.ts` invokes it every minute, while `bookings.service.ts` starts a separate five-minute interval with a different policy source. Photography hold is 10 minutes. | Expiry can overwrite concurrent paid/consented booking and release inventory; inconsistent deadlines confuse the guard. | Consolidate semantics against persisted hold, CAS by status/hold/revision, concurrent cleanup vs payment/consent test; do not introduce a new duration. | Booking team; disable V2 flow, correct affected booking via audited reconciliation. |
| R7 | High | Contract consent re-reads hold inside transaction; concurrent expiry in isolation was tested, but cancellation/item mutation can commit after read. | Stale accepted version or payment bound to changed item. | Booking revision/contract binding CAS; mutation paths invalidate unbound offers; stress tests for reschedule, item edit, cancel and consent/payment. | Booking + contract; supersede new offers, preserve old versions. |
| R8 | High | Provider AUTO acceptance revocation is checked during consent, but after-consent/unpaid rule is undecided. | Inconsistent readiness and unfair provider/customer expectation. | Approve revocation cutoff; serialize with payment binding; tests before/during/after consent and payment. | Product/legal + contracts; block new offers while unresolved. |
| R9 | High | `WebhookEventRepository` dedupes by order/status; PAID may arrive after FAILED/EXPIRED/CANCELLED or hold expiry. | Repeated/out-of-order events create wrong booking/refund outcome. | Durable event state, gateway verification, terminal ordering and late-payment reconciliation; duplicate/out-of-order test matrix. | Payments/finance; acknowledge money event, mark review, no automatic stock allocation. |
| R10 | High | Current Phase 4.5 tests check service/database behavior; no real JWT HTTP test or deployed log redaction test. | Cross-tenant access or sensitive evidence leakage. | Real signed JWT e2e for owner/other customer/provider/admin, forged actor, expiry, idempotency, log sink assertions. | Security/backend; keep flag OFF until pass. |
| R11 | High | Combo pricing may include shared voucher, service fee or deposit, while contract is per rental provider. | Provider-specific contract price is wrong or invented. | Approve allocation rules and reconcile sum to booking amount; block affected combo cases until rule exists. | Product/finance; disable multi-provider combo V2. |
| R12 | High | Only service-level concurrency and test DB index tests were previously run; Docker API is permission-denied in this audit. | False sense of runtime verification. | Restore isolated DB access; rerun complete integration and combined race tests; record commands/exit codes. | QA/backend; do not enable flag. |
| R13 | Medium | Full Jest run had 8 failures, reproduced on unchanged HEAD with same dependencies. | New regressions could be hidden among baseline failures. | Maintain exact 8-failure baseline list; compare each new run; targeted suites must pass independently. | QA; block new or changed failures, do not expand Phase 5 scope to unrelated repairs. |
| R14 | Medium | PDF artifact generation can fail after consent/payment; document metadata exists but no finalized worker. | Customer may lack downloadable copy though evidence exists. | Separate async retry, private storage and hash verification; do not couple contract state to PDF success. | Contracts/operations; retain source evidence, retry renderer after separate approval. |
| R15 | Medium | Feature flag OFF and legacy booking marker null are compatibility protections; a broad guard could accidentally block legacy/photography. | Existing checkout regression. | Explicit V2 opt-in branch, legacy/photography/remaining-payment regression tests and canary metrics. | Backend/payments; turn off new V2 initiation while allowing in-flight recovery. |
| R16 | Medium | Webhook signature bypass is allowed when checksum key absent for local simulator. | Misconfigured nonlocal environment could accept forged payments. | Deployment configuration gate, signed webhook e2e, simulator disabled in production. | DevOps/security; stop webhook activation and investigate transactions. |

No risk is marked closed by this document. Phase 5 implementation requires acceptance criteria and rollback from `PHASE5_PLAN.md` plus explicit approvals in `PHASE5_APPROVAL_CHECKLIST.md`.
