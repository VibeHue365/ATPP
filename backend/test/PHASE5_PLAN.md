### Unresolved races requiring a Phase 5 implementation gate

1. The expiry check is a transactional read, but the booking cleanup path in `booking-status.service.ts` selects pending bookings then calls `updateManyBookings` by ID without a status predicate. A concurrent payment/consent transition can be overwritten by cleanup. `bookings-scheduler.service.ts` calls that path every minute. `bookings.service.ts` also starts a five-minute interval on application bootstrap with a separate expiry cleanup path. They use different hold sources: 15-minute `SYSTEM_POLICIES.BOOKING_HOLD_TIMEOUT_MS` versus `PolicyResolverService.getBookingHoldPolicy()` (default 15 minutes, configurable), while photography hold uses a 10-minute `HOLD_DURATION_MS`. Normalize the active paths against persisted `holdExpiresAt` and require compare-and-set on status/hold before release; do not invent a new duration.
2. `assertSourcesUnchanged` reads booking/items inside consent's transaction; a separate item edit, cancellation or reschedule may commit immediately after it. A payment guard must revalidate and atomically bind the accepted version(s) to the payment and booking revision. All source mutations must invalidate an unbound offer, and bound mutations require an explicit amendment/compensation rule.
3. Provider revocation is rechecked inside consent transaction, but revocation after consent must not erase historical consent. Define whether already accepted, unpaid offers remain payable; this needs business approval. Avoid revocation racing with new payment binding by checking the selected policy in the same serialized boundary.
4. `finalizeAfterPayment` is a multi-step workflow, not one transaction. A webhook, polling request and admin/simulator confirmation can race. A successful payment may be stored before booking/inventory/contract finalization finishes; use durable idempotent reconciliation and a review state.

## 2. Current and proposed flow

Current: `CartPage.tsx` (and `BookingCheckoutModal.tsx`, `PhotographerDetailPage.tsx`) → booking creation/holds → `POST /payments/create-link` → pending or zero-value SUCCESS payment → `GET /payments/:code/status`, simulator confirm, admin confirm or PayOS webhook → `PaymentsService.confirmPayment` / `finalizeAfterPayment` → booking, inventory, voucher, notification and settlement effects. `GET /payments/:code/status` currently auto-confirms pending sandbox payments, so it is a mutation path. `GET /payments/pending-checkouts` only lists existing payments.

Proposed V2 rental flow: approved template + provider mechanism acceptance → backend creates provider-specific immutable contract versions → issue OFFERED version(s) tied to live booking/hold → customer accepts **every rental provider's current version** → atomic readiness check and binding at payment creation/reuse → payment attempt → every success/failure finalization path verifies binding and current booking state → durable contract/booking outcome or reconciliation queue. Photography-only and legacy bookings follow their existing paths while the flag is off. A combo gets contracts only for providers with rental `PRODUCT` items, not all `providerIds`.

### Contract meaning and timestamps — proposed, pending business/legal approval

- Provider AUTO_ACCEPTANCE means recorded consent to a versioned **mechanism** and policy scope before an individual booking. It is not by itself acceptance of each transaction and this design does not label it an electronic signature.
- Customer `ACCEPT` is evidence of an in-app decision on exact rendered text, content hash and booking fingerprint. Whether this and provider's mechanism produce a legally recognized electronic signature or legally binding contract requires separate business/legal approval. No code should label a contract “signed” solely from this technical event.
- Proposed `customerAcceptedAt`: time the consent transaction commits (the stored server `occurredAt` is captured inside that transaction). `formedAt`: only when the approved transaction-formation rule is satisfied; leave null until that rule is approved. `effectiveAt`: only upon the approved effectiveness trigger; do not infer it from payment or PDF creation. `paidAt`: timestamp of verified successful payment, independent of formation/effectiveness. Store all as separate server-side fields/events.
- Immutable evidence: retain original snapshot, exact rendered text, template/mechanism versions, `contentHash`, `bookingFingerprint`, provider acceptance ID and timing, customer consent, payment binding and event IDs. New terms require a new version; never rewrite prior evidence. PDF is a reproducible artifact of that evidence and may be generated asynchronously; its failure must not alter hashes or decisions.

### Proposed state transition matrix

`DigitalContract` is stable identity `(bookingId,providerId,scope)`; `ContractVersion.state` is the lifecycle state. Payment has its own `PENDING/SUCCESS/FAILED/CANCELLED` state. Booking statuses remain governed by existing booking code. Transition operations must use atomic predicates and stable event/idempotency keys.

Exact schema state inventory: `ContractVersion` declares `DRAFT`, `PENDING_PROVIDER`, `OFFERED`, `ACCEPTED`, `EFFECTIVE`, `SUPERSEDED`, `DECLINED`, `EXPIRED`, `TERMINATED`; `PENDING_PROVIDER` is reserved for the unimplemented manual mode and must stay unreachable in the AUTO MVP. Legacy `DigitalContract.status` is separately `DRAFT/SIGNED/VOID` and must not be used as a V2 state shortcut. `Payment.status` is `PENDING/PROCESSING/SUCCESS/FAILED/CANCELLED`; `PROCESSING` is reserved for a durable finalization/recovery step, not proof of money receipt. `Booking.status` is `DRAFT/PENDING_PAYMENT/DEPOSIT_PAID/CONFIRMED/PICKUP_PENDING/PICKED_UP/RETURN_PENDING/RETURNED/IN_PROGRESS/AWAITING_REVIEW/COMBO_PHOTOS_APPROVED/COMPLETED/CANCELLED/DISPUTED/PARTIALLY_REFUNDED/REFUNDED`. Phase 5 touches only the payment boundary (`PENDING_PAYMENT` to existing paid/confirmed outcomes, or cancellation/review); later rental/photography statuses remain owned by their existing services. Its booking/payment CAS must reject a stale `PENDING_PAYMENT` assumption, while late money is recorded separately for review.

| Event | Preconditions | Version before → after | Booking/payment effect | Idempotency and failure |
| --- | --- | --- | --- | --- |
| Prepare | V2 marker, live pending booking/hold, rental item, approved template/mechanism, active provider acceptance, safe indexes | none → `DRAFT`; unchanged current version → same version; changed snapshot → new `DRAFT`, old unaccepted `DRAFT/OFFERED` → `SUPERSEDED` | None | Unique identity/version indexes; retry returns same version. Reject stale source or missing index. Existing `ACCEPTED` evidence stays immutable; amendment rule needed before new version. |
| Provider mechanism accept | Authenticated provider owner, approved mechanism/policy version | No version change; provider acceptance `ACTIVE` | None | One active `(provider,scope)`; retry same hash is stable, different hash requires new record/review. |
| Offer issuance (new in Phase 5) | Current `DRAFT`, current fingerprint, all provider prerequisites, live hold, approved template | `DRAFT` → `OFFERED`, set offer expiry no later than existing hold | None | CAS current version; retry returns same offer. Do not issue after expiry. No new hold duration is invented. |
| Customer ACCEPT | Owner, current `OFFERED`, exact hashes, live hold, active provider mechanism | `OFFERED` → `ACCEPTED`; one immutable `ContractConsent` | No payment yet | Existing transaction/unique indexes; same-key retry returns same result, opposite or reused key conflicts. |
| Customer DECLINE | Same authorization/freshness checks | `OFFERED` → `DECLINED`; immutable consent | Block payment for this offer | Same-key retry stable; ACCEPT after DECLINE conflicts. Re-offer requires new version and business rule. |
| Booking/item amendment | Booking edit/reschedule before payment binding | Current unaccepted → `SUPERSEDED`; new `DRAFT` on prepare. Accepted version remains historical; readiness becomes stale | Existing pending link must be invalidated or explicitly re-bound; do not silently use it | CAS booking revision; preserve old evidence. If payment already in flight, route to conflict/reconciliation. |
| Hold expiry / booking cancellation | Live hold elapsed or authorized cancellation | Unaccepted `DRAFT/OFFERED` → `EXPIRED/TERMINATED`; accepted evidence preserved, technical status may become `TERMINATED` only with approved semantics | Booking cancellation/release existing holds; pending payment closed according to current policy | CAS booking status/hold; concurrent payment needs one winner; paid-late case is reviewed/refunded per existing policy. No deletion of consent. |
| Provider mechanism revocation | Provider owner, active acceptance | Historical versions/consents unchanged; future prepare/offer blocked | Whether existing accepted unpaid offers remain payable is **OPEN** | CAS active acceptance; retain historical record/timestamp. |
| Payment initiate/reuse | All provider versions accepted and current; booking/holds live; binding matches exact versions/fingerprint | `ACCEPTED` unchanged | New `PENDING` payment or existing pending link with same binding; zero-value path must still pass guard | One payment intent per booking/purpose; reject stale link. Binding creation and booking guard must serialize. |
| Verified payment success | PayOS verified or authorized simulator/admin/polling path, existing bound payment | `ACCEPTED` → `EFFECTIVE` **only if effectiveness rule approved**; otherwise retain accepted state and record payment event | Payment `PENDING` → `SUCCESS`, booking/inventory finalized exactly once | Unique webhook event + payment CAS + durable finalization record; duplicate returns prior outcome. If contract finalization fails after money success, persist review/retry, never pretend unpaid. |
| Payment failure/timeout | Verified terminal gateway event or existing timeout rule | Accepted version retained until offer/hold expires or booking closes | Payment `PENDING` → `FAILED/CANCELLED`; release only through approved booking policy | Duplicate terminal event no-op. A later PAID event is a late-payment reconciliation, not a silent overwrite. |
| Late PAID webhook | Funds verified but booking expired/cancelled, hold lost, binding stale/missing, or failure previously recorded | Do not revive/alter accepted evidence automatically | Record successful money receipt and `paymentReviewRequired`; refund/reconciliation through existing guarded path | Dedupe by gateway event/order; retry side effects via durable job; never allocate released stock silently. |
| PDF success/failure | Immutable version and authorized renderer | No contract state change | Artifact metadata `PENDING→READY/FAILED`; retry failed rendering | Deterministic source/hash; private storage; failure must not roll back paid money or consent. PDF itself is outside Phase 5 until separately approved. |

Read-only post-change checks, to run only after an independently approved migration, are `db.digital_contracts.getIndexes()`, `db.contract_versions.getIndexes()`, `db.contract_consents.getIndexes()`, `db.provider_contract_acceptances.getIndexes()`, the duplicate aggregates above, and counts by `flowVersion/status` before versus after. Inspect `db.payments.countDocuments({'contractBinding.flowVersion':2})` and orphan binding/version references with read-only joins. Do not paste connection strings or contract text into logs. To produce the existing **dry-run only** report from `backend/`, supply an explicitly reviewed URI through the process environment and run `node scripts/migrate-contract-v2.js --dry-run`; save its fingerprint and conflict count. There is deliberately no application-DB `--apply` command in this plan because the current script rejects such a target.

Also preflight: missing IDs/code/scope, orphan booking or provider, customer/provider mismatch, invalid legacy `SIGNED` evidence, non-rental booking marked for rental, incomplete V2 currentVersion pointer, duplicate payment binding, and changing records between scan and apply. `scripts/migrate-contract-v2.js --dry-run` is read-only and reports a fingerprint. Its `--apply` path is deliberately **test DB only** and does **not** create/drop indexes; it must not be repurposed for the application DB. A separate reviewed production runbook/tool with explicit target allowlist, fingerprint, progress journal and operator approval is a Phase 5 dependency.

Rollout order: (1) freeze V2 writes/flag OFF; (2) take verified backup and restore rehearsal on isolated DB; (3) run preflight + dry-run on explicit target; (4) resolve conflicts by review, never invent signatures; (5) execute reviewed idempotent legacy-marker migration with checkpointed batches; (6) verify counts/fingerprint and legacy evidence; (7) build new unique indexes while old booking index still exists; (8) verify index definitions and replica health; (9) drop old booking-only unique index only under approved window; (10) run read-only checks and one isolated smoke path; (11) enable flag only by separate approval/canary. No step here is executed by this document.

If migration stops halfway, keep flag OFF and payment V2 guard inactive, inspect journal and read-only counts, rerun idempotent backfill from a new dry-run/fingerprint. If the new index failed, retain old index. If old index was dropped **before any V2 multi-provider write**, restore it or restore backup after an approved outage. After multi-provider writes, recreating old booking-only unique index may be impossible; prefer roll-forward, isolate V2 traffic and restore from backup only after an explicit data-loss/reconciliation decision. Legacy `SIGNED` records and signatures are never deleted or rewritten.

## 4. HTTP security verification plan

Use a separate replica-set DB and real Nest HTTP server/auth module. Obtain real signed JWTs via the configured test auth path for customer A/B, provider A/B and admin; no mocked `@CurrentUser` in these tests. Cover expired/invalid JWT (401), role and provider ownership (403/404), cross-tenant reads/consents, hidden resource existence, forged `actorUserId`/role in request JSON (ignored or rejected), altered hash/fingerprint, same-key retry, different-key conflicting retry, key reuse across contracts, concurrent requests, and provider revocation. Assert database rows **and** HTTP response for each case. Capture application logs with test sink and assert no JWT, refresh token, full contract text, private storage key or unnecessary PII. Verify webhook signature behavior separately with configured checksum key; simulator is explicitly disabled outside development/test.

## 5. Payment readiness architecture and entry-point inventory

| Entry point | Current behavior / file | Proposed guard |
| --- | --- | --- |
| `POST /payments/create-link` | `payments.controller.ts` → `PaymentsService.createPaymentLink`; returns existing pending payment early; amount ≤0 creates SUCCESS and finalizes | Authorize booking, evaluate **all** rental-provider readiness and hold, atomically bind exact versions/fingerprint before both reuse and new/zero payment. Never reuse an unbound/stale V2 link. Photography-only and legacy route via explicit compatibility branch. |
| `GET /payments/:code/status` | `getPaymentStatus` may call `confirmPayment` for pending payment | Treat as finalization entry; make read-only status or run the same binding/finalization guard in central service. Do not rely on controller-only validation. |
| `POST /payments/:code/confirm` | Admin manual confirm | Central service verifies binding, gateway/admin authority and booking state. Admin cannot bypass V2 evidence; exceptional override needs separate audited business approval. |
| `POST /payments/checkout/:code/confirm` | Development simulator confirm | Same central guard; simulator gating remains. |
| `POST /payments/webhook` | PayOS PAID → confirm; FAILED/EXPIRED/CANCELLED → fail; `WebhookEventRepository` dedupes events | Verify signature/amount/order, claim event, then central payment guard. For late PAID, acknowledge durable receipt and queue review/refund reconciliation instead of rejecting and looping forever. Deduplication must include terminal status ordering and finalization progress, not only event ID. |
| `POST /payments/checkout/:code/cancel` | Simulator cancel → `failPayment` | Retain current cancellation policy; close bound intent idempotently, preserve contract consent. |
| `GET /payments/pending-checkouts` | Lists pending links | Read-only; filter or label stale V2 links so UI cannot resume unsafe checkout. |
| Frontend payment initiators | `CartPage.tsx`, `BookingCheckoutModal.tsx`, `PhotographerDetailPage.tsx` | Future UX shows provider-specific offers/consent first. Photography-only path remains unchanged. Frontend cannot attest readiness on behalf of backend. |

Use a single backend `ContractPaymentReadinessGuard`/orchestration function at the service boundary, called by initiation **and** finalization. It must read booking, rental item set, current accepted versions, consent rows, template/mechanism IDs, holds and `Payment.contractBinding`; compare the exact provider set, content hashes and booking fingerprint. Serialization proposal: booking revision / payment-intent CAS in a Mongo transaction for local records, with no network PayOS call inside the transaction. Persist intent/binding before external payment. PayOS calls and booking effects use durable retry/outbox semantics. Preserve existing payment paths for non-V2 bookings and staged feature-flag rollout. Late money receipt is a financial event even when contract readiness is false: record it, set review, never silently confirm rental, and use existing refund workflow only after policy review.

## 7. Decisions required before Phase 5 implementation

1. Approve exact áo dài template, policy version, and provider AUTO mechanism wording; legal review must decide whether/how the in-app records are characterized. Otherwise offers remain DRAFT.
2. Decide `formedAt` and `effectiveAt` triggers separately: customer acceptance, provider-specific acceptance condition, verified payment, delivery, or another approved event. Do not conflate timestamps.
3. Decide whether provider revocation blocks only future offers or also accepted but unpaid offers; historical evidence remains.
4. Decide how amendment, cancellation and DECLINE affect re-offer and an already opened payment link.
5. Decide allocation of voucher, shared fees and deposits across providers in a combo. If no auditable rule, multi-provider combo V2 remains blocked.
6. Approve late-payment handling/refund authority and whether an admin may override readiness (recommended: no silent override; any exception needs independent audited workflow).
7. Approve production DB backup/window, read-only preflight, migration operator, restore test and canary/rollback thresholds.

Stop here. No Phase 5 implementation or activation is authorized by this plan.
